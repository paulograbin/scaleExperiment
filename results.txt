  - Minor collections (6–14ms) — the generational part is working. Young objects (request allocations) get collected cheaply every ~300ms.
  This is ideal.
  - "Allocation Rate" trigger — ZGC sees you're filling the heap fast (~400M every 300ms ≈ 1.3 GB/s allocation rate) and collects younggen
  before you hit the ceiling.
  - "High Usage" trigger — you hit ~90% heap, ZGC steps in immediately.
  - Major collections (~40ms) — still happen every ~3s to clean up objects that survived to old gen. 40ms is a bit high but only happens
  occasionally.

  The allocation rate is very high (~1.3 GB/s). For a hello-world returning a static string, that's suspicious. Quarkus/Vert.x might be
  allocating request/response buffers per request. Under heavy load this is normal — it's all short-lived garbage that minor GC handleswell.

  Verdict: This is healthy GC behavior. Sub-15ms minor pauses at high throughput are good. If you want to squeeze further, you could try
  -Xmx1g to give more breathing room between collections and reduce frequency.

  ├───────────────────────┼───────────┼─────────────────────────────────────────────┤
  │ Live data after major │ 64–92M    │ 8–86M                                       │
  ├───────────────────────┼───────────┼─────────────────────────────────────────────┤
  │ Allocation rate       │ ~1.3 GB/s │ ~3 GB/s (higher frequency, smaller batches) │
  └───────────────────────┴───────────┴─────────────────────────────────────────────┘

  Key observations:

  1. Major collections are 2-3x faster (9–19ms vs 39–49ms) — less old-gen garbage to scan, fewer complex objects.
  2. Final major GC tells the story — 236M→8M — only 8MB of actual live data. The pure Java server's working set is tiny compared to
  Quarkus's 64-86M (no CDI contexts, no routing maps, no Netty pools).
  3. Still allocating a lot (~3 GB/s) — that's virtual thread stacks and the HttpExchange objects the JDK creates per request. The JDK's
   com.sun.net.httpserver isn't zero-allocation, but the objects are simpler and die young.
  4. GC(246) at the end — load stopped, proactive GC cleaned everything down to 8MB. That's your true baseline footprint.

  This is about as good as it gets without going to raw NIO (which would eliminate the per-request HttpExchange allocations). How are
  the req/s numbers comparing?

GC is the same as before
Still ~100k read errors — so the backlog wasn't the bottleneck. The problem is in com.sun.net.httpserver itself. Its internal
  implementation uses a single selector thread to accept connections and dispatch to the executor. At 192k req/s with 400 connections it
   can't keep up, so connections get reset.

  This is a known limitation of the JDK's built-in HTTP server — it wasn't designed for this load level.

  Your options:

  1. Accept it — 192k req/s is still great, the errors are just wrk overwhelming the accept loop. In a real scenario you wouldn't have
  400 connections hammering from localhost.
  2. Reduce connections — wrk -t4 -c100 -d30s will likely give you zero errors and still 100k+ req/s. This tests throughput without
  overloading the accept queue.
  3. Go raw NIO — write a custom event loop with java.nio.channels.Selector + virtual threads. Eliminates the HttpServer bottleneck
  entirely, but significantly more code.
